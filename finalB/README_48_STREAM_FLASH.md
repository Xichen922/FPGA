# finalB：B 板曲谱流式写入 W25Q64

## 串口屏“当前模式”显示（10 月 31 日更新）

与 `D:\FPGA\26competition\嵌赛.HMI` 的新版页面配套：上电及停止后显示“手动”，`P` 自动播放期间显示“自动”，`G` 普通跟弹和 `H` 简单跟弹期间均显示“辅助”。模式以 B 板真实的 `score_playing` / `guide_active` 状态为准，曲谱播完也会自动回到“手动”。

陶晶驰编辑器截图确认“当前模式”对应 `t15`。此前 FPGA 把音效强度百分比写入 `t15`，这正是卡片显示数字 `0` 的原因。现改为 `t15.txt` 只显示“手动／自动／辅助”；音效强度只更新原有 `j0.val` 进度条，不再写 `t15`。上电后和每约 3 秒会重发模式文字。B 板烧录本目录新生成的 `impl/pnr/finalB.fs`；A 板及屏幕工程无需修改。

ModelSim 验证手动→自动→辅助→手动四次状态更新及 `t15` 写入；原按键、音色/音效、频谱串口仿真均通过。Gowin 综合、布局布线及位流生成通过，setup/hold 违规端点数均为 0。实屏显示仍需上板确认。

## 实现范围

以 example47 为基础。A 板、A/B 板 SPI、串口屏、DAC、音色与音效控制保持原接线。B 板取消 512 条曲谱 RAM；一条曲谱事件经 HC-06 到达后，直接写入 W25Q64 并读回核验，成功才向手机回 `K\n`。自动播放 `P`、普通跟弹 `G`、简单跟弹 `H` 都按索引从闪存取谱。当前上限 **8192 条转换后的事件**，不是 MIDI 原始音符数。

使用 W25Q64 最后一个 64 KiB 扇区 `0x7F0000–0x7FFFFF`，本版实际使用前 32 KiB。`C` 擦除整个扇区，覆盖 46 测试数据及 47 曲谱。每次 B 板上电/重烧后事件数量归零；虽然闪存字节仍可能保留，本版没有断电恢复索引，必须重新 `C`、上传。这是明确的会话语义。

## 接线与烧录

与 47 完全相同：闪存 `VCC→B 板 3.3 V`、`GND→B 板 GND`、`CS→J3-1/K2`、`CLK→J3-2/K1`、`DI→J3-3/L1`、`DO→J3-4/L2`。A/B 其余连接不动。B 板烧录 `impl/pnr/finalB.fs`。A 板无需改动。功放音量先调低。

## 板端蓝牙协议 048

HC-06 仍为 SPP 透明串口，9600、8N1；发送 ASCII 文本行，每行以 LF (`0A`) 结束；CR (`0D`) 可在 LF 前出现。单条事件格式、掩码、音区/音色/音效字段、`P/G/H/S/?/V` 的含义沿用 44 工程。

| 发送 | 回复 | 含义 |
|---|---|---|
| `V\n` | `V=048\n` | 协议版本 |
| `C\n` | `K\n` 或 `X\n` | 擦除曲谱扇区；**擦除完成后**才回复，可能等数秒 |
| `M001,100,4,0,0\n` 等事件行 | `K\n` / `E\n` / `B\n` / `F\n` / `X\n` | `K` 表示写入并读回一致，已计数 |
| `?\n` | `N=dddd\n` | 四位十进制已提交事件数，如 `N=0513`、`N=8192` |
| `P\n` / `G\n` / `H\n` | `K\n` 或 `Z\n` / `B\n` | 自动播放/普通跟弹/简单跟弹 |
| `S\n` | `K\n` | 停止播放或跟弹 |

`E`=语法错误，`B`=设备正忙或曲谱尚未初始化，`F`=达到 8192，`Z`=空曲谱，`X`=闪存 ID/擦除/写入或读回核验失败。遇 `X` 不要跳过该事件继续上传；应停止、检查供电和接线，再 `C` 重新上传。`K` 是单行确认，须逐行等待，不能连续倾倒所有行。上电后等 B 板启动约 1 秒，再发 `C`；在 `C` 的 `K` 到来前不要发事件。

**注意**：本版 `N=dddd` 固定四位，旧版是三位。旧 App 的数量解析、版本判断和 512 条上限需要更新。旧 App 未更新前可用串口蓝牙助手手动验证短谱；不能据此宣称旧 App 可稳定上传长谱。

## 给 App 队友的改动

1. 支持 `V=048`；解析 `N=0000` 到 `N=8192`，使用四位十进制。可继续兼容旧 `V=042` 与三位数量回复，按版本决定上限。
2. 将 048 固件的板端**事件数**上限从 512 提到 8192。转换、轨道合并、分段预览和上传校验须统计最终事件行，不能用 MIDI note-on 数量代替。原有音乐/曲库不需改文件格式。
3. 上传顺序：必要时先发 `S` 并等 `K`；发送 `C`，等待其 `K`（建议擦除超时 ≥10 秒）；再逐行发送转换后的事件，每行严格等待 `K` 才推进已上传计数；最后 `?`，核对 `N=dddd` 等于本段事件数，然后才允许 `P/G/H`。单条事件建议超时 ≥3 秒，并可展示正在写闪存。不要以发送出去的行数作为成功数。
4. `X` 为不可继续的存储失败；`B` 可在短暂等待后重试，但 `C` 超时/`X` 后需重新初始化；`F` 提示容量满。若在一次上传中途断电、断线或出现 `X`，**不要从旧索引盲目续传**，重新 `C` 全量上传。进度由 `?` 的已提交数量核对。
5. `P/G/H` 回复仍是进入模式的确认；自动播放和跟弹目标键会从闪存读取，App 不需新增跟弹目标传输。保留 App 的现有跟弹界面与屏幕功能。板端目前无播放/跟弹完成异步上报，App 原来的结束判断策略仍适用。
6. 0.5.0 的自动分段建议可保留，但把“1–512 条可上传”改成“1–8192 条”；优先整首可上传时不强行分段，超过容量才按原乐句/休止候选规划。转换器本身不用限制 512 条。

## 分步调试

1. 保留 47 位流作为回退；核对闪存接线及 3.3 V，然后烧录 48 位流到 **B 板**。A 板保持当前可工作的版本。
2. 用蓝牙助手或新版 App 发送 `V`，应收到 `V=048`；发送 `?`，应收到 `N=0000`。若旧 App 只识别 `V=042`，先用助手测试。
3. 发送 `C`，等待 `K`；擦除期间别发送下一行。再发 `?`，应为 `N=0000`。
4. 发 `M001,100,4,0,0`、`M002,100,4,0,0` 两行，每行等 `K`；发 `?`，应得到 `N=0002`。按 `P` 测声音顺序，再 `S`；按 `G` 和 `H`，分别确认屏幕目标键和按对后前进。每次模式切换先 `S`。
5. 用新版 App 上传一首 **超过 512、少于 8193 条最终事件**的曲谱，期间每条等待 `K`；最终 `N=dddd` 要与预览事件数相等。再分别测自动播放和跟弹。使用同一份 47 可正常播放的短曲做听感对照；不能仅凭“有声音”判断音序正确。
6. 若 `C` 收到 `X`，先回到 46 工程核对 JEDEC ID/PASS，再检查供电共地和四根 SPI 线。若上传卡住，检查 App 是否把擦除等待设得过短、是否按 LF 发文本、是否错误解析四位数量。若 `N` 正确而无声音，检查 A/B 链路与 B 板是否烧录了 48 位流。

## 验证与限制

- ModelSim：闪存模拟验证擦除、逐条写入、读回、第 513 条、第 8192 条和满额拒绝；自动播放与 G/H 均从闪存取目标；蓝牙协议验证延迟 `K`、`N=0513`、`V=048`。
- Gowin V1.9.12.04：综合、布局布线和位流生成完成；50 MHz 约束下实际 Fmax 60.344 MHz，setup/hold TNS 均为 0；BSRAM 40/56。本版尚未在真实双板加 App 上板验收。
- 每次 `C` 擦除 64 KiB；频繁重传会消耗闪存擦写寿命，比赛调试的正常次数通常远低于器件标称寿命，但本版不做磨损均衡。
- 本版仍只存一首当前曲谱，不提供多首曲库索引或断电续传；手机 App 仍保存原 MIDI/曲库，并可随时重新上传另一首。
